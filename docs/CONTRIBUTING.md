# 协作与发布流程

## 环境

只需要 Node（跑测试）和一个静态服务器。Python 仅在需要用 `pinkuro_server.py` 做本地代理时才会用到。

```bash
python -m http.server 8787      # 或 npx serve -l 8787 .
node test_golden.js             # 跑测试
```

## 改动一次的标准流程

1. **改代码** —— 数值口径优先改 `data/*.json`，不要为了调一个常量去动引擎。
2. **跑测试** —— 至少跑 `test_golden.js`、`test_server_split.js`，以及你改到的模块对应的 `test_*.js`。
3. **升版本号** —— 见下一节。
4. **提交** —— 提交信息用中文，写清改了什么、对玩家可感知的结果有什么变化。
5. **推送** —— 推到 `main`，GitHub Pages 会自动构建，通常 20–80 秒生效。
6. **验证线上** —— 用真实浏览器打开线上地址，确认改动生效、没有报错。

## 版本号规则

样式与脚本通过查询参数破缓存，格式固定为 `?v=YYYYMMDDx`（`x` 为当天序号 `a`、`b`、`c`…）：

- **只升改过的文件**，没动的文件保持原版本号。
- `index.html` 与 `mobile.html` 引用的是同一个文件时，两处的版本号要一起改。
- `tools.json` 由外壳以 `?ts=` 拉取，**改它不需要升版本号**；但里面注册的 `entry` 带了 `?v=` 的，那个版本号要跟着改。
- 不要用批量替换脚本统一刷版本号，容易把没改的文件也带上。

## 提交规范

- **只 `git add` 具体文件**，不要用 `-A` 或 `.`。这个仓库有多个来源并行提交，一把梭会把别人的半成品带进来。
- 临时脚本、调试产物、运行输出不要进仓库。浏览器自动化脚本统一用 `_cdp_` 前缀并在 `.gitignore` 中排除。
- 行尾：仓库内是 LF，Windows 检出为 CRLF（`core.autocrlf=true`）。不要整文件改行尾，会让 diff 淹没真实改动。

## 验证要求

改前端不能只看代码，要看渲染结果：

- **桌面与手机都要验**。两端共用 `js/app.js`，但布局是两套。
- 用无头浏览器做端到端验证时，手机视口必须显式设置设备尺寸（`Emulation.setDeviceMetricsOverride`）。只加窗口参数 `--window-size=390,844` 时，headless 的实际视口仍是 500px 宽，会让「无横向溢出」的断言误报通过。
- 断言要落在 DOM 结果上（元素存在、文本数值、尺寸），不要只断言「点了没报错」。

## 发布

| 站点 | 触发方式 |
|---|---|
| GitHub Pages（主站） | 推送到 `main` 后自动构建 |
| WorkBuddy 镜像 | 需要单独发布一次，内容必须与主站同一提交 |

推送成功不等于上线。判断 Pages 是否真的更新，看响应头 `Last-Modified` 是否对得上本次提交时间；对不上说明构建还没跑完或卡住了，可以到 Actions 里重跑 `pages-build-deployment`。

## 不要提交的内容

- `pinkuro_server.py`（本地代理）
- `_cdp_*.js` 与各类 `*_out.txt`（调试产物）
- `__pycache__/`、编辑器与系统临时文件

以上都已在 `.gitignore` 中处理，新增类似文件时请一并补进去。
